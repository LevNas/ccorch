# DEC-007: One job per pane — the wrapper sets where it works, a cover note says the rest

- **Status**: Accepted (2026-10-20). Implemented and unit-tested (0.7.0). Not yet checked live: a real job pane started by `/ccorch:job` (see Consequences).
- **Complements**: DEC-004 and DEC-005 (the three pane conditions stand), DEC-006 (auto mode, the start gate and the deny rules apply to a job pane too).

## Context

Most pane work was not `/ccor`'s split into Main Brain, children and grandchildren. It was one task handed to one pane, started by hand: open a tmux pane in the target repository, start `claude`, paste the request, watch the pane. ccorch had no procedure for that, so each request was written from scratch, and two things went wrong:

- A request said "make a branch and work there". The pane did not use a worktree: it switched the repository's main checkout to the branch, which stayed off the default branch until the merge.
- A request said "do not delete working files with `rm`". The pane wrote a script with `rm -rf` and stopped at the user's ask rule.

What leaked was not the task but the conditions the pane works under. And a ban written in the request did not hold.

## Decision

1. **A job mode in the wrapper.** `CCORCH_MODE=job` with `CCORCH_WORKTREE=<name>` starts a depth-1 pane that does one task itself:
   - `claude --worktree <name>` is the first argument, so Claude Code creates the worktree and isolates the session in it. Where the pane works is set by the wrapper, not asked for in text.
   - `Bash(tmux *)` is added to the deny rules: a job starts no panes. The Agent tool and `git push` stay allowed (a job may use subagents and may open a pull request).
   - The start gate refuses a job at depth 2 or 3, a job with `CCORCH_PARENT_ID`, a job without `CCORCH_WORKTREE`, a worktree name outside letters, digits, `.`, `_` and `-` (not starting with `.` or `-`, no `..`, at most 64 characters), and any other `CCORCH_MODE`.
   - The system prompt replaces the Main Brain sections with a "Single job" section and a result format of five sections: Summary, Evidence, Not tested, Branch and PR, Left behind.
   - Without `CCORCH_MODE`, the claude argv and the system prompt are unchanged byte for byte (`CCORCH_WORKTREE` alone is not read).
2. **A skill, `/ccorch:job`, and two scripts.**
   - `scripts/ccorch-job.sh` starts the pane. It gives tmux the command as separate arguments (`bash -c 'exec bash "$0" "$(cat "$1")"' <wrapper> <task file>`), so no shell parses the task text or the paths, and the pane's program is the wrapper (its `pane-died` hook needs that).
   - `scripts/ccorch-wait.sh` is `/ccor`'s wait loop as one command, so a session isolated in a worktree, which refuses commands with loops, can run it.
   - The skill writes the **cover note**: where the pane works, the repository's rules, where working files go, what to return, what to do when stopped. It says what to do instead of relying on bans, and points to the mechanisms that hold.
3. **Content and cover note are separate.** What the task is (pointers to issues and files, the next skill, nothing secret) is the content. The skill uses a project's `arc-handoff` skill for it when the session has one (ccharness scaffolds it), and otherwise writes the same three things itself. ccorch owns only the cover note, because only ccorch knows about panes.

## Why

- **Mechanism over text for the place of work.** The failure was a pane choosing where to work. A worktree created by `claude --worktree` takes that choice away; a sentence in the request did not.
- **Text for the rest, phrased as what to do.** The repository's rules and the return format cannot be set by flags. The `rm` case shows a ban in text does not bind, so the cover note says where working files go and that the caller cleans up.
- **Scripts for the deterministic steps.** Starting the pane and waiting give the same answer for the same input, so they are scripts, tested without tmux or claude. Building a shell string for tmux from a multi-line task with quotes is where hand-written commands break.

## Consequences

- A job pane is still a whole session: the skill sends work that meets none of the three pane conditions to a subagent instead.
- Each job has its own session ID and work directory, so `CCORCH_MAX_PANES` counts the panes of one job, not of all jobs. Two jobs at once are not limited by the gate.
- Unit tests: `tests/test_wrapper.sh` (job mode: argv, deny rules, prompt, refusals, a real start against the fake claude) and `tests/test_job.sh` (the launcher's tmux arguments and refusals, the wait script, the skill's five cover-note sections). Each added check was seen to fail on a deliberately broken copy.
- Checked by hand, not in the tests: on tmux 3.7b, `new-window` with the command as separate arguments ran it with the tmux server as parent (no shell), `-e` values arrived intact, and a multi-line task with quotes and `$` reached the program unchanged.
- Not checked live yet: a real job pane (that `claude --worktree` with `--append-system-prompt` and the pasted task behaves as expected, where the new branch starts, that the pane writes its result file in the session directory from inside the worktree, and that the main checkout stays on its branch).

## Rejected alternatives

- **Add the cover note to `/ccor`'s Main Brain prompt.** The smallest change, but the failures happened in panes started by hand, which `/ccor` does not cover.
- **Start the job pane with plain `claude`, as before.** No start gate, no auto mode by flag, no deny rules; and the place of work would again be a sentence in the request.
- **Put the cover note in ccharness's `arc-handoff`.** Then ccharness would need to know about panes; it covers the work inside one session.
- **Build the tmux command as a shell string.** The task text would need quoting for the user's shell; a quote or `$` in it breaks the command or runs something.
