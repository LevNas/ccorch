# DEC-006: Panes run in auto mode; limits are enforced by a start gate

- **Status**: Accepted (2026-10-04). Implemented and unit-tested (0.6.0), and verified by the live check on 2026-10-04 (results in issue #11): the requirements that depend on it (REQ-004, REQ-008, NFR-SEC-001 to 003, US-002, US-004) are Verified. The live check did not run a denied command or start a Grandchild; those parts rest on `tests/test_wrapper.sh` (see Consequences). On 2026-10-05 a live check of 0.6.2 with one Main Brain passed for `--add-dir` and for two 0.6.1 changes as they apply to the Main Brain (its signal after `result.md`, the Write-tool instructions); 0.6.1's changes for children (signalling at every turn, the parent waiting again), `/ccor`'s wait loop and the wrapper's re-copy on exit were not exercised (see Consequences).
- **Complements**: DEC-002 (environment variables for depth propagation). DEC-002 chose how depth and limits travel; this decision makes the wrapper check them. DEC-002's note that `--disallowedTools "Agent"` was "meant as structural enforcement" is replaced by the gate and deny rules below.
- **Fixes**: issue #9

## Decision

1. **Panes start with `--permission-mode auto`**, not `--dangerously-skip-permissions`. `--allowedTools` is dropped.
2. **A computed start gate** in `scripts/ccorch-wrapper.sh` refuses a start, before `claude` runs, when a limit is not a positive integer, when the depth is not 1, 2 or 3, when `tmux list-panes` fails, when the depth does not follow from the parent's recorded depth, when the live ccorch panes would exceed `CCORCH_MAX_PANES`, or when the live siblings under one parent would exceed `CCORCH_MAX_CHILDREN_D1` (depth 2) or `CCORCH_MAX_CHILDREN_D2` (depth 3). A refusal is a result file with `status: refused` and a reason; the parent is signalled by the existing trap.
3. **A per-depth deny list** through `--disallowedTools`, one rule per argv element:
   - every depth: `Bash(rm -rf *)`, `Bash(rm -fr *)`, `Bash(rm -Rf *)`, `Bash(rm -r -f *)`, `Bash(rm -f -r *)`, `Bash(rm -r --force *)`, `Bash(rm --recursive *)`, `Bash(git push --force *)`, `Bash(git push *--force*)`, `Bash(git push -f *)`, `Bash(git push * -f*)`, `Bash(git push * +*)`, `Bash(git push *--delete*)`, `Bash(git push * :*)`, `Bash(git branch -D *)`, `Bash(git reset --hard *)`, `Bash(git clean *)`, `Bash(sudo *)`
   - depth 2 and 3 add `Bash(git push *)` and `Bash(git -C * push*)`: only the Main Brain is meant to push
   - depth 3 adds `Agent` and `Bash(tmux *)`
4. **The limits are passed down explicitly.** The `tmux split-pane` templates in the system prompt carry `CCORCH_MAX_PANES`, `CCORCH_MAX_CHILDREN_D1`, `CCORCH_MAX_CHILDREN_D2` and `CCORCH_PARENT_ID`.

## Why

From the official documentation (checked 2026-10-04):

- Permission modes: "Deny rules block in every mode, including `bypassPermissions`." and "Allow rules have no effect in `bypassPermissions`." So with the bypass, `--allowedTools` restricted nothing; only `--disallowedTools "Agent"` at depth 3 held.
- Permissions: "A bare tool name like `Bash` removes the tool from Claude's context entirely, so Claude never sees it." (this is why `Agent` is a bare deny). Scoped Bash rules match the command text after compound commands are split and a fixed set of wrappers stripped, and "a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program."
- The old allow string `Bash(git:status,git:diff,git:add,git:commit,tmux:*)` is one literal prefix (commas are not a list separator in the documented syntax). It matched no command.
- Auto mode's classifier blocks by default "Launching an autonomous agent loop that runs without human approval or a sandbox, such as one started with `--dangerously-skip-permissions`". The bypass is therefore the thing auto mode is built to stop, and running children in auto mode puts a classifier between the pane and the shell.

Two further gaps showed up while fixing this: `CCORCH_MAX_PANES` reached the wrapper and was compared with nothing, and `CCORCH_MAX_CHILDREN_D1/D2` never reached child panes, because a pane made with `tmux split-pane "<cmd>"` takes its environment from the tmux server, not from the calling process.

Because Bash deny rules are not a boundary, the limits that matter (depth, pane count, children per parent) are enforced by code that computes the answer, not by rules or prompt text. The gate is the boundary for those; the classifier is the boundary for what a pane runs.

## Details of the gate

- It runs after `CHILD_ID`, the result file and `trap cleanup EXIT` exist, and before the watchdog starts, so a refusal reaches the parent.
- Live panes are the `*.pane` files in the work directory whose id appears in `tmux list-panes -a -F '#{pane_id}'`. If that command fails the gate refuses; it does not count every recorded pane as dead. The current pane is excluded from the count, and the pane's own `.pane`, `.parent` and `.depth` files are written only after the checks pass, so the count never includes the pane being started. The user's own pane is not in the count: with `CCORCH_MAX_PANES=3` the Main Brain plus two children fit, and there is no room for grandchildren.
- **Depth is derived, not declared.** Each started pane records its depth in `<id>.depth`. At depth 2 and 3 the gate requires the parent's `.pane` and `.depth` records and a live parent pane, takes the parent's depth plus 1 as the effective depth, and refuses if `CCORCH_DEPTH` disagrees (the reason names both numbers). The effective depth drives the deny list, the children limit and the prompt. A start with no `CCORCH_PARENT_ID` must claim depth 1, and only one live depth-1 record is allowed per work directory (one Main Brain per session).
- The sibling limit follows the pane's own effective depth: depth 2 uses `CCORCH_MAX_CHILDREN_D1`, depth 3 uses `CCORCH_MAX_CHILDREN_D2`. Depth 1 has no parent and skips the sibling check.
- Limits that are not positive integers are refused, naming the variable.
- A `mkdir` lock on `$WORK_DIR/.lock.d` is held from counting until the records are written, so simultaneous starts cannot both pass. It is a bounded wait, then refuse; a lock left by a killed wrapper is removed by hand (the refusal names it). The holder writes its PID to `.lock.d/owner`; if that write fails the lock is removed and the start is refused ("lock: cannot write owner"). The wait is `CCORCH_LOCK_WAIT` seconds (default 10, at most 6 digits), tried every 0.1 s; on timeout the refusal names the lock directory and the owner pid when readable, and says "if no ccorch pane is running, remove this directory and retry". Nothing else removes a lock, so there is no ownership comparison: `release_lock` clears `LOCK_HELD` first (a signal during the release cannot release twice), then removes the owner file and the directory. It is called from `cleanup()` because bash keeps one EXIT trap and a second one would replace the signalling cleanup. The lock replaced `flock` (util-linux only, absent on macOS). Automatic stale-lock recovery was tried (owner liveness, lock age, atomic rename with a re-check) and each version had a new race; it was removed in favour of a refusal that a person acts on.
- **The parent is always signalled.** `cleanup()` starts with `set +e`, guards every write (result file, `mv`, `result.md` copy, lock release), kills the watchdog, and sends `tmux wait-for -S` last, so a work directory that cannot be written still ends in a signal. Only a dry run skips the signal, because it must not touch a live channel. `refuse()` and the watchdog guard their writes the same way. A wrapper killed with SIGKILL runs no trap; since 0.6.3 the pane's tmux `pane-died` hook writes an error result and signals instead ([wrapper-script.md](../components/wrapper-script.md), "Signal on SIGKILL, from tmux").
- **Trap order.** The only checks before `trap cleanup EXIT` are `CCORCH_WORK_DIR` and `CCORCH_PARENT_CHANNEL` (without a work directory there is nowhere to write a result, and without a channel nothing to signal, so the wrapper prints to stderr and exits 2). Everything after the trap, including a missing task argument, a `PROJECT_DIR` that does not exist and a bad `CCORCH_TIMEOUT`, is a `refuse()` and so reaches the parent. Paths are made absolute before any `cd`.
- **Dry runs read, never write, the live session.** The gate reads `WORK_DIR` without a lock (nothing is recorded, so a race does not matter). Every write goes to a fresh temporary `OUT_DIR`, printed on the first line of the output: the result file, `status.md` and the prompt dump. A dry run neither creates a missing `WORK_DIR` nor leaves a phantom result in a live one.
- **The Main Brain's result reaches the user's session.** At depth 1 `cleanup()` copies the result file to `result.md` when that is absent, so a refused, error, incomplete or timed-out Main Brain is visible to the skill's read path. A child, a pane that claims depth 1 under a parent, and a start refused because a Main Brain is already running do not write `result.md`. (Since 0.6.1 the Stop hook also copies the Main Brain's result to `result.md` before signalling, and `cleanup()` copies again when the wrapper ran `claude` and the content differs; a wrapper refused before `claude` started still never replaces an existing `result.md`. The cost: if a `result.md` from an earlier run is left in the same work directory, a refusal is not copied over it, so the skill reads the old result; `/ccor` creates a new work directory for each session, so this needs a reused `CCORCH_WORK_DIR`. See [wrapper-script.md](../components/wrapper-script.md#completion-signal-the-stop-hook-and-resultmd).)
- Front-matter values (`depth:`, `task:`, `reason:`) are sanitized to one line with no double quotes or backslashes, so a value from the environment or the task cannot add a second `status:` line. The depth label in `CHILD_ID` is 1, 2, 3, or `x`.

**What the gate bounds.** The gate bounds a model that uses the documented launch command. A process that rewrites its own environment, picks a new `CCORCH_WORK_DIR`, or runs `claude` directly can still escape it. Against that, the boundary is the auto-mode classifier, not the gate.

## Consequences

- Children can stop and wait for a human when the classifier blocks an action. The skill and the system prompt say so.
- Where auto mode is not available to the pane's session (an unsupported model, the `disableAutoMode` setting, or turned off by Anthropic), Claude Code starts the pane in Manual mode, so every pane prompts before most actions. The gate and the deny rules do not depend on the mode. README, the getting-started guides and the 0.6.0 "Upgrading" notes say so.
- The depth 3 deny of `Bash(tmux *)` also removes `tmux wait-for` from that pane; the Stop hook signals the parent, so nothing depends on it.
- The gate guards the wrapper path. A process that runs `claude` directly, bypassing the wrapper, is outside it.
- If `claude` exits without writing a result file, the wrapper records `status: error` with the exit code when it exited non-zero, and `status: incomplete` when it exited 0. It no longer reports `success`.
- Live check (2026-10-04, 0.6.0, Claude Code v2.1.288; issue #11): the Main Brain started a child with `tmux split-pane … --permission-mode auto` without a classifier prompt in both runs; the Main Brain and the child ran in auto mode; a child over `CCORCH_MAX_PANES` and one over `CCORCH_MAX_CHILDREN_D1` came back `status: refused` with the reason, and the parent read it. The requirements listed in Status are Verified. Not exercised live: a denied command (the dry run showed the 18 deny rules reach `claude`), and a Grandchild (depth 3 deny rules).
- The live check also found two problems, fixed in 0.6.1 (#13): the user's session was signalled before `result.md` existed, and the prompt's `mv`-based writes stopped at a user's ask rule on `mv`.
- The 0.6.1 live check (2026-10-05, Claude Code v2.1.288) stopped at the Main Brain's first Read of `status.md`: a read outside the working directories asked for approval in auto mode. 0.6.2 passes the session directory with `--add-dir`. 0.6.1's own changes were not reached, so they have not been checked live.
- The 0.6.2 live check (2026-10-05, same setup; issue #11): the Main Brain read and wrote `status.md` and wrote its result file with the file tools without a prompt; with the user's ask rule on `mv` still set, it followed the prompt, wrote with the Write tool and ran no `mv` (none of its four Bash commands contains `mv`), which shows the prompt avoids `mv`, not how `mv` would have fared; the first signal on the session channel came with `result.md` present while the pane was still running, 4 s after the result was written. A second signal came 3 s later, also with `result.md`, for a reason not found. The Main Brain finished in a single turn, so the run does not show the hook staying silent at an earlier turn with no result. Not exercised live: a child that runs (children signal at every turn and the parent waits again), the `/ccor` skill's own wait loop, a Grandchild, and a denied command.

## Known gaps of the deny rules

The rules are the common forms, not a closed list. Known gaps: other flag spellings and orderings, full paths (`/bin/rm`), `sh -c '...'`, aliases and wrapper scripts, and any command that reaches the same effect another way. They reduce accidents in the usual command form; the auto-mode classifier and the start gate are the boundaries.

## Rejected alternatives

- **Keep the bypass and rely on `--disallowedTools`.** Deny rules do hold under the bypass, but they are not a boundary for Bash, and the bypass is what auto mode's classifier exists to prevent.
- **Fix the allowlist syntax.** Allow rules have no effect under the bypass, and under auto mode an allowlist is not needed to enforce depth.
- **Enforce limits in the system prompt only.** A prompt can be ignored or injected; the limits would hold only as far as the model complied.
- **Parse the parent id for the depth.** Fragile; the parent's recorded depth is used instead.
- **Trust `CCORCH_DEPTH` from the environment.** A pane could declare any depth and pick its own deny list and limits; the recorded parent depth is authoritative.
- **Recover stale locks automatically.** Every variant (dead owner, lock age, rename and put back) produced a new race; a bounded wait and a refusal that names the lock is simpler and can be acted on.
- **Keep `flock` and warn where it is missing.** That left the gate without a lock on macOS; the `mkdir` lock works on both.
