# DEC-006: Panes run in auto mode; limits are enforced by a start gate

- **Status**: Accepted (2026-10-04)
- **Complements**: DEC-002 (environment variables for depth propagation). DEC-002 chose how depth and limits travel; this decision makes the wrapper check them. DEC-002's note that `--disallowedTools "Agent"` was "meant as structural enforcement" is replaced by the gate and deny rules below.
- **Fixes**: issue #9

## Decision

1. **Panes start with `--permission-mode auto`**, not `--dangerously-skip-permissions`. `--allowedTools` is dropped.
2. **A computed start gate** in `scripts/ccorch-wrapper.sh` refuses a start, before `claude` runs, when the depth is not 1, 2 or 3, when the live ccorch panes would exceed `CCORCH_MAX_PANES`, or when the live siblings under one parent would exceed `CCORCH_MAX_CHILDREN_D1` (depth 2) or `CCORCH_MAX_CHILDREN_D2` (depth 3). A refusal is a result file with `status: refused` and a reason; the parent is signalled by the existing trap.
3. **A per-depth deny list** through `--disallowedTools`, one rule per argv element:
   - every depth: `Bash(rm -rf *)`, `Bash(git push --force *)`, `Bash(git push -f *)`, `Bash(git reset --hard *)`, `Bash(git clean *)`, `Bash(sudo *)`
   - depth 2 and 3 add `Bash(git push *)`: only the Main Brain pushes
   - depth 3 adds `Agent` and `Bash(tmux *)`
4. **The limits are passed down explicitly.** The `tmux split-pane` templates in the system prompt carry `CCORCH_MAX_PANES`, `CCORCH_MAX_CHILDREN_D1`, `CCORCH_MAX_CHILDREN_D2` and `CCORCH_PARENT_ID`.

## Why

From the official documentation (checked 2026-10-04):

- Permission modes: "Deny rules block in every mode, including `bypassPermissions`." and "Allow rules have no effect in `bypassPermissions`." So with the bypass, `--allowedTools` restricted nothing; only `--disallowedTools "Agent"` at depth 3 held.
- Permissions: "A bare tool name like `Bash` removes the tool from Claude's context entirely, so Claude never sees it." (this is why `Agent` is a bare deny). Scoped Bash rules match the command text after compound commands are split and a fixed set of wrappers stripped, and "a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program."
- The old allow string `Bash(git:status,git:diff,git:add,git:commit,tmux:*)` is one literal prefix (commas are not a list separator in the documented syntax). It matched no command.
- Auto mode's classifier blocks by default "Launching an autonomous agent loop that runs without human approval or a sandbox, such as one started with `--dangerously-skip-permissions`". The bypass is therefore the thing auto mode is built to stop, and running children in auto mode puts a classifier between the pane and the shell.

Two further gaps showed up while fixing this: `CCORCH_MAX_PANES` reached the wrapper and was compared with nothing, and `CCORCH_MAX_CHILDREN_D1/D2` never reached child panes, because a pane made with `tmux split-pane "<cmd>"` takes its environment from the tmux server, not from the calling process.

Because Bash deny rules are not a boundary, the limits that matter (depth, pane count, children per parent) are enforced by code that computes the answer, not by rules or prompt text. The gate is the boundary for those; the classifier is the boundary for what a pane runs.

## Details of the gate

- It runs after `CHILD_ID`, the result file and `trap cleanup EXIT` exist, and before the watchdog starts, so a refusal reaches the parent.
- Live panes are the `*.pane` files in the work directory whose id appears in `tmux list-panes -a -F '#{pane_id}'`. The current pane is excluded from the count, and the pane's own `.pane` and `.parent` files are written only after the checks pass, so the count never includes the pane being started. The user's own pane is not in the count: with `CCORCH_MAX_PANES=3` the Main Brain plus two children fit, and there is no room for grandchildren.
- The sibling limit follows the pane's own depth, not a parse of the parent id. Depth 1 has no parent and skips the sibling check. At depth 2 and 3 a missing `CCORCH_PARENT_ID` is itself a refusal, since the siblings could not be counted.
- A `flock` on `$WORK_DIR/.lock` is held from counting until the files are written, so simultaneous starts cannot both pass. The lock descriptor is closed before any subshell or `claude` starts. `flock` is from util-linux and is not on macOS; without it the wrapper prints a one-line warning and counts without the lock instead of refusing, so the plugin still works there.

## Consequences

- Children can stop and wait for a human when the classifier blocks an action. The skill and the system prompt say so.
- The depth 3 deny of `Bash(tmux *)` also removes `tmux wait-for` from that pane; the Stop hook signals the parent, so nothing depends on it.
- The gate guards the wrapper path. A process that runs `claude` directly, bypassing the wrapper, is outside it.
- A live check is still needed after release: that the Main Brain can start a child in auto mode without the classifier blocking it, and that an over-limit child comes back `refused`.

## Rejected alternatives

- **Keep the bypass and rely on `--disallowedTools`.** Deny rules do hold under the bypass, but they are not a boundary for Bash, and the bypass is what auto mode's classifier exists to prevent.
- **Fix the allowlist syntax.** Allow rules have no effect under the bypass, and under auto mode an allowlist is not needed to enforce depth.
- **Enforce limits in the system prompt only.** A prompt can be ignored or injected; the limits would hold only as far as the model complied.
- **Parse the parent id for the depth.** Fragile; the pane's own depth is already known.
